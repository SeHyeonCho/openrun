# 부하 측정 명세

전략 비교 단계(P1)에서 좌석 잠금 방식을 같은 조건으로 비교하려고 정한 측정 방법이다. 무엇을, 어떤 부하로, 얼마 동안 재고, 무엇을 통과로 보는지를 정한다. k6 스크립트와 측정 결과는 이 문서를 따른다.

- 목표 수치의 출처: [README 목표 수치](../../README.md#-목표-수치)
- 잠금 순서와 판단 시각: [ADR 0003](../adr/0003-잠금-순서와-판단-시각.md)
- 값마다 성격을 붙인다. **측정**은 공개 자료에서 온 값, **가정**은 근거 자료 없이 정한 값, **계산**은 식으로 구한 값, **판단**은 공개 기준을 찾지 못해 공학적으로 정한 값이다

## 1. 부하 모형

### 1.1 입력값

| 기호 | 뜻 | 기준 부하 | 스트레스 부하 | 성격 |
|---|---|---:|---:|---|
| S | 판매 좌석 수 | 300 | 500 | 가정. 회차당 지원 범위(30~500석) 안에서 고른 값 |
| r | 좌석당 판매 오픈 순간의 실수요(사람 수 ÷ 좌석 수) | 1 | 10 | 가정 |
| b | 세션 배수. 한 사람이 여는 기기·탭 수와 봇 | 1.2 | 1/(1−0.4) ≈ 1.667 | 기준은 가정, 스트레스는 악성 봇 비율 40%(측정, 벤더 수치)에서 계산 |
| W | 첫 클릭이 몰리는 시간 | 60초 | 10초 | 가정 |
| c | W 안에 선점을 누르는 세션 비율 | 0.9 | 0.9 | 가정 |
| 입장 호출 | 한 세션이 들어올 때 보내는 조회 수 | 3회 | 3회 | 가정 |
| 새로고침 간격 | 머무는 동안 공연 페이지를 다시 읽는 간격 | 3초 | 3초 | 가정 |
| 재시도 배수 | 첫 선점 시도에 대한 전체 선점 요청의 배수 | 2 | 2 | 가정. 상한으로 쓴다 |
| 주문당 매수 | 1매 59%, 2매 41%, 평균 1.41매 | | | 측정(콘서트 1인 1매 비율 59%) |

식에 들어가는 측정값은 악성 봇 비율과 1인 1매 비율 두 개다. 공연 시장 통계(KOPIS 회차당 평균 예매 수)는 좌석 범위를 고르는 근거로만 썼다. 나머지는 가정이므로, 실제 판매 기록이 생기면 바로 바꾼다.

### 1.2 계산

| 값 | 식 | 기준 부하 | 스트레스 부하 | README |
|---|---|---:|---:|---|
| 구매자 수 | S × r | 300 | 5,000 | |
| 세션 수 N | S × r × b | 360 | 8,333 | 360 / 8,300 |
| 세션 도착률 | N ÷ W | 초당 6 | 초당 833 | |
| 조회 RPS | N × (입장 호출 ÷ W + 1 ÷ 새로고침 간격) | 138 | 5,278 | 140 / 5,300 |
| 그중 새로고침 | N ÷ 새로고침 간격 | 120 | 2,778 | |
| 첫 선점 시도/초 | N × c ÷ W | 5.4 | 750 | |
| 선점 요청/초 | 첫 선점 시도 × 재시도 배수 | 10.8 | 1,500 | 11 / 1,500 |
| 매진에 필요한 주문 | S ÷ 1.41 | 213 | 355 | |
| 첫 시도만으로 매진까지 | 필요한 주문 ÷ 첫 선점 시도/초 | 약 39초 | 약 0.5초 | |

README의 값은 이 표를 반올림한 것이다. 조회 RPS와 선점 요청/초는 **러시 구간 W 동안 모든 세션이 머물며 새로고침하고, 선점하는 세션이 모두 한 번씩 다시 보낸다고 본 상한**이다. 2.4절의 세션은 선점 요청을 최대 두 번(첫 요청과 다시 보내기 한 번) 보내므로 러시 구간 평균 선점 요청/초는 이 값을 넘지 않는다. 세션이 무작위로 도착하므로 순간 값은 넘을 수 있다. 실제 측정에서는 세션이 선점에 성공하거나 떠나면 요청을 멈추므로 이보다 적게 나올 수 있어, 실제로 나온 값을 함께 기록한다(5.1절). 소진 뒤 구간의 취소표 재선점(2.4절 8단계)은 러시 구간 밖이라 이 상한에 넣지 않고 따로 기록한다.

**가정이 필요 없는 상한:** 선점 성공은 좌석 수를 넘을 수 없다. 꼭 필요한 성공 쓰기는 좌석 수 ÷ 매진 시간이다. 300석이 1분 만에 매진되면 초당 5건이고, 스트레스 부하의 선점 요청 1,500건/초 가운데 대부분은 거절되어야 할 요청이다. 그래서 스트레스 부하에서 보는 것은 잠금 성능보다 **거절 응답을 얼마나 싸게 돌려주는가**다.

### 1.3 지금 화면·실제 사용과 다른 가정

- **새로고침:** 구매자 화면은 공연 페이지를 정해진 간격으로 다시 읽지 않는다. 캐시가 5초 지나면 화면을 다시 열거나 창으로 돌아올 때 다시 읽는다. 조회 RPS의 대부분(기준 120 / 138)은 "판매 오픈 순간 사람들이 새로고침한다"는 가정에서 나온 부하다. 지금 화면 그대로라면 조회 부하는 이보다 훨씬 적다
- **좌석 선택:** 지정석은 세션마다 좌석 목록을 한 번 읽고, 그중 비어 보이는 좌석을 무작위로 고른다(2.4절). 실제로는 앞자리에 몰리므로, 무작위 선택은 경합을 실제보다 낮게 잡을 수 있다
- **봇과 여러 기기:** 남는 세션(2.4절)은 모두 이미 있는 구매자의 추가 세션으로 둔다. 스트레스 부하의 세션 배수는 악성 봇 비율에서 나왔지만, 봇이 계정을 여러 개 쓰는 경우는 반영하지 않는다. 그래서 1인 최대 좌석 수 거절이 실제보다 많이 나올 수 있다
- **응답 유실:** 응답을 받지 못해 같은 식별자로 다시 보내는 화면 동작은 부하에 넣지 않는다. 그 경로는 동시성 테스트와 화면 테스트가 확인한다

## 2. 측정 대상과 시나리오

### 2.1 비교 대상

| 좌석 종류 | 전략 | 비고 |
|---|---|---|
| 지정석 | 지금 방식: 좌석 ID 순 `FOR UPDATE` | 기본 |
| 지정석 | 방어 없음 | 측정 전용. 초과 판매를 재현하려는 기준선이라 판정하지 않는다 |
| 지정석 | 조건부 `UPDATE`(상태가 `AVAILABLE`이거나 기한이 지난 좌석만 바꾸고 영향 행 수로 판단) | |
| 지정석 | 낙관적 락(버전 열) | |
| 자유석 | 지금 방식: `FOR UPDATE SKIP LOCKED` | 기본 |
| 자유석 | 조건부 `UPDATE` | |

모든 전략에서 ADR 0003의 1·2단계(선점 요청 기록, 구매자 잠금)는 같다. 바꾸는 것은 3단계(좌석)뿐이다. 구매자 잠금을 바꾸면 1인 최대 좌석 수 규칙이 달라져 좌석 잠금끼리의 비교가 되지 않는다. 확정·취소는 비교하지 않고 모든 전략에서 지금 방식을 쓴다.

### 2.2 시나리오

| 시나리오 | 부하 | 목적 |
|---|---|---|
| 기준 부하 | 1절의 기준 입력 | 반드시 통과해야 한다 |
| 스트레스 부하 | 1절의 스트레스 입력 | 판매 오픈 직후 요청이 몰릴 때의 동작을 기록한다. 지연 저하는 허용한다 |
| 경계 탐색 | 기준 부하에서 r만 1, 2, 4, 8, 16, 32로 두 배씩 올린다(S 300, W 60초). r=1 단계는 기준 부하와 같은 조건이라 기준 부하 결과를 그대로 쓴다 | 기준 부하 판정을 처음 어기는 단계와 그때의 병목을 찾는다 |
| 민감도 | (r, W) = (1, 60초), (3, 30초), (10, 10초), S 300. (1, 60초)는 기준 부하와 같은 조건이라 기준 부하 결과를 그대로 쓴다 | 결과를 가장 크게 흔드는 두 가정을 함께 바꿨을 때 기준 부하 판정을 여전히 지키는지 본다. 판정은 기준 부하 열로 한다 |

각 시나리오를 지정석과 자유석에서 따로 돌린다. 방어 없음은 판정하지 않는 기준선이라 기준 부하와 스트레스 부하에서만 돌리고, 판정을 어기는 단계를 찾는 경계 탐색과 민감도에서는 돌리지 않는다. 민감도의 세 조합에서 조회 RPS는 138, 468, 2,280, 선점 요청/초는 10.8, 64.8, 648이다(계산). 아홉 조합을 모두 돌리지 않고 대각선 세 조합만 보는 것은 측정 시간이 너무 길어서다.

### 2.3 구간

| 구간 | 기준 부하 | 스트레스 부하 | 하는 일 |
|---|---|---|---|
| 준비 | 1분 | 1분 | 별도 준비용 공연을 초당 1세션으로 조회만 한다. 서버와 DB를 데운다. 이 구간은 결과에 넣지 않는다 |
| 러시 | W(60초) | W(10초) | 판매가 열리는 순간부터 세션이 도착률 N ÷ W로 고르게 도착한다 |
| 소진 뒤 | 3분 | 3분 | 새 세션은 오지 않는다. 확정, 취소, 선점 기한 만료, 취소표 재선점이 일어난다 |

판매 시작 시각은 준비 구간이 끝나기 1초 전으로 정한다. 세션이 판매가 열리기 직전에 도착해 `SALES_NOT_OPEN`을 받는 일이 없게 하려는 것이다. 측정은 러시와 소진 뒤 구간을 합쳐서 낸다. **측정 끝**은 소진 뒤 구간이 끝나는 순간이다. 이때 새 요청을 멈추고, 아직 보내지 않은 요청(확정, 취소, 선점)은 보내지 않는다. 이미 보낸 요청은 끝날 때까지 기다린다(k6 시나리오의 `gracefulStop` 30초). 요청 제한 시간은 구매자 화면과 같은 10초이고, 넘기면 응답 없음으로 센다. 진행 중이던 요청의 응답도 지표에 넣는다. 서버는 요청 제한 시간이 없어서, 클라이언트가 10초 뒤 포기한 선점도 서버에서는 커넥션 풀이나 DB 잠금을 기다리며 계속될 수 있다(잠금 대기 상한 `innodb_lock_wait_timeout` 50초). 그래서 측정 끝 뒤에는 이 순서로 마무리한다. ① k6가 새 요청을 멈추고 보낸 요청을 기다린다 ② 앱을 정상 종료(graceful shutdown)해 서버가 받은 요청을 모두 끝낸다 ③ 앱 프로세스가 끝난 시각을 **집계 시각**으로 하고 DB 집계(5.1절)를 한다. 앱이 멈춘 뒤에는 새 커밋이 생길 수 없어서, 연결을 기다리던 요청이나 첫 SQL을 실행하기 전이던 요청도 집계에서 빠지지 않는다. 정상 종료 대기 시간은 잠금 대기 상한보다 긴 60초로 측정용 설정에 명시하고, 그 안에 종료가 끝나지 않으면 4절의 서버 실패로 기록한다. 클라이언트에서 제한 시간을 넘긴 요청은 응답 시간에서 응답 없음으로 세고, 서버에서 커밋됐다면 그 주문은 불변식과 매진 시간 집계에 들어간다.

### 2.4 한 세션의 흐름

| 단계 | 요청 | 확률·간격 | 성격 |
|---|---|---|---|
| 1. 입장 | `GET /api/me`, `GET /api/performances/{id}`, 그리고 자유석은 `GET /api/showtimes/{id}/availability`, 지정석은 `GET /api/showtimes/{id}/seats` | 도착 즉시 3회 | 가정 |
| 2. 머무름 | `GET /api/performances/{id}` | 3초마다. 선점에 성공하거나 떠날 때까지 읽는다. 선점하지 않는 세션은 러시 구간이 끝나면 떠난다 | 가정 |
| 3. 선점 시도 | `POST /api/orders` | 세션의 90%가 입장 뒤 1~3초 사이(무작위)에 보낸다. 나머지 10%는 선점하지 않고 머무르다 떠난다 | 가정 |
| 4. 매수 | 1매 59%, 2매 41% | | 측정 |
| 5. 좌석 고르기(지정석) | 1단계에서 읽은 좌석 목록 가운데 비어 보이는 좌석을 무작위로 고른다 | | 가정 |
| 6. 실패하면 | `SEAT_NOT_AVAILABLE`이면 구매 가능 수(지정석은 좌석 목록)를 다시 읽고 다른 좌석으로 다시 보낸다. 다시 보내기는 한 번뿐이고, 남은 좌석이 0이면 보내지 않는다. 다시 보낸 요청도 실패하거나 `SEAT_LIMIT_EXCEEDED`, `SALES_CLOSED`를 받으면 선점을 멈추고 8단계로 간다 | | 가정. 선점 요청이 세션당 최대 두 번이라 1절의 재시도 배수 2가 러시 구간의 상한이 된다 |
| 7. 성공하면 | `GET /api/orders/{token}` 한 번, 30~90초 뒤 다음 중 하나 | 확정 90%, 취소 5%, 기한까지 둠 5% | 가정 |
| 8. 선점에 실패해 멈춘 세션 | 30%는 취소표를 기다린다. 소진 뒤 구간 동안 3초마다 구매 가능 수를 보고, 남은 수가 생길 때마다 선점을 한 번 보낸다. 성공하면 7단계로 가고, 실패하면 계속 기다린다. 소진 뒤 구간이 끝나면 떠난다. 70%는 바로 떠난다. 측정 끝(2.3절) 전에 7단계의 대기 시간이 끝나지 않은 주문은 확정·취소하지 않은 채 선점 상태로 남는다 | | 가정 |

선점 요청마다 새 `Idempotency-Key`를 쓰고, `Expected-Buyer-Id`는 그 세션의 구매자다. 세션 N 가운데 구매자 수(S × r)만큼은 서로 다른 구매자이고, 남는 세션(기준 60개, 스트레스 3,333개)은 이미 있는 구매자 가운데 무작위로 고른 사람의 다른 기기다. 그래서 같은 구매자의 동시 선점과 1인 최대 좌석 수가 부하 안에서도 일어난다.

## 3. 측정 데이터

| 항목 | 값 |
|---|---|
| 공연·회차 | 측정용 공연 하나, 회차 하나. 준비 구간용 공연은 따로 둔다 |
| 좌석 | 지정석은 S석(300석은 15행 × 20열, 500석은 20행 × 25열), 자유석은 S개 |
| 1인 최대 좌석 수 | 4 |
| 선점 유지 시간 | **2분**(측정용). 소진 뒤 구간 3분 안에 기한 만료와 재선점이 일어나게 하려는 값이다. 실제 회차 기본값(10분)과 다르다 |
| 판매 시작 | 준비 구간이 끝나기 1초 전(2.3절) |
| 판매 마감 | 집계 시각(2.3절) 뒤. 진행 중인 요청이 판매 마감으로 거부되지 않게 한다 |
| 구매자 | S × r명. 부하 테스트용 로그인 경로로 로그인한다(다음 이슈) |
| 초기화 | 측정마다 측정용 데이터를 지우고 다시 만든다. 이전 측정의 주문·선점 요청 기록이 남지 않게 한다 |

## 4. 측정 조건

- **반복:** 같은 시나리오·전략을 3번 돌린다. 성능 지표(응답 시간, 실패 비율, 실제 부하)는 3번의 중앙값을 결과로 쓰고 최솟값과 최댓값도 함께 적는다. 서버 실패와 불변식(확정 중복, 선점 중첩, 1인 한도 초과)은 중앙값을 내지 않고 반복마다 본다(5.2절의 3번 판정)
- **경계 탐색의 반복:** 판정은 언제나 3번을 잰 결과(5.2절의 3번 판정)로 한다. 한 번 측정은 어느 단계를 3번 잴지 고르는 탐색에만 쓴다. r=1은 기준 부하 결과(3번)를 쓴다
  1. r=2부터 한 번씩 올려, 처음 판정을 어기는 단계 k를 찾는다. 한 번 잰 결과는 서버 실패, 불변식 위반, 응답 시간·실패 비율 기준 위반 가운데 하나라도 있으면 어긴 것으로 본다
  2. k를 3번 잰다. 3번 판정을 지키면 k를 통과로 보고 k 위 단계부터 1번을 이어 간다
  3. k의 3번 판정을 어기면 k 바로 아래 단계를 3번 잰다. 그것도 어기면 다시 한 단계 아래를 3번 재는 식으로, 3번 판정을 지키는 단계가 나올 때까지 내려간다. 이미 3번 잰 단계는 다시 재지 않는다
  4. 탐색이 r=32에 이르러 r=32의 한 번 측정이 판정을 지키면(앞 단계를 3번 재서 통과한 경우를 포함한다) r=32를 3번 잰다. 3번 판정을 지키면 경계는 r=32 이상(하한)이고, 어기면 3번처럼 내려간다
  5. 경계는 3번 판정을 지킨 가장 높은 단계다. 그 바로 위 단계는 3번 판정을 어긴 단계다(r=32 이상인 경우는 빼고)
  6. 내려가다 r=1(기준 부하)까지 판정을 어기면 그 전략은 기준 부하 미달이고, 최대 처리량은 "측정 범위 아래"로 적는다
- **앱 다시 띄우기:** 측정마다 데이터를 초기화하고 측정 끝에 앱을 종료하므로(2.3절), 측정마다 앱을 새로 띄운다. 전략은 앱을 띄울 때 정한다
- **부하 모델:** k6의 개방형 모델(`ramping-arrival-rate`)로 세션을 도착시킨다. 서버가 느려져도 도착률이 줄지 않아야 몰리는 상황을 잴 수 있다
- **판정 순서:** 측정이 끝나면 서버 실패인지 먼저 보고, 서버 실패가 아닐 때만 무효인지 본다. 둘 다 아니면 결과로 쓴다. 서버 실패는 그 시나리오의 판정을 어긴 것으로 본다
- **서버 실패로 보는 경우:** 측정 중 앱 프로세스가 죽거나, 30초 동안 어떤 요청에도 응답하지 않거나(요청 제한 시간 10초의 세 배라 몇몇 요청이 느린 것과 구분된다), 서버가 연결을 거부했거나, 측정 끝 뒤 앱 정상 종료가 60초 안에 끝나지 않으면(2.3절) 다른 조건과 상관없이 서버 실패로 기록한다. 경계 탐색에서는 그 단계를 무너진 지점으로 보고, 원인(메모리 부족, 커넥션 풀 고갈, 스레드 고갈 등)을 앱 로그와 함께 적는다. 이때 k6가 정한 속도를 다 내지 못했으면 실제로 들어간 부하(조회 RPS, 선점 요청/초)를 함께 적는다. 연결 거부가 서버 쪽인지 k6 쪽인지는 같은 시각의 앱 상태(프로세스, 로그)로 가른다
- **측정을 무효로 보는 경우:** 서버가 살아 있는 측정에서 다음 가운데 하나라도 있으면 무효다. k6가 정한 속도로 보내지 못한 요청(`dropped_iterations` > 0), k6 프로세스 CPU 사용률 80% 초과, k6 쪽에서만 생기는 오류(로컬 포트 고갈 등). 서버 한계가 아니라 부하 발생기 한계를 잰 것이라 결과로 쓰지 않고 다시 잰다. 부하 발생기 한계로 같은 조건이 3번 연속 무효면 "이 장비로는 잴 수 없음"으로 기록하고, 배포 환경이나 부하 발생기를 분리한 환경에서 잰다. 노트북에서는 스트레스 부하가 여기에 걸릴 수 있다
- **예상 밖 응답도 무효로 본다:** 5.1절의 예상 밖 응답이 한 건이라도 있으면 측정 도구, 설정, 서버 결함 가운데 하나를 잰 것이라 무효다. 원인을 기록하고 고친 뒤 다시 잰다. 원인이 서버 결함이면 이슈로 남긴다. 이 경우는 장비 한계가 아니므로 3번 연속 무효 규칙을 쓰지 않는다
- **기록할 환경**
  - 장비: CPU 모델·코어 수, 메모리, OS, k6와 서버가 같은 장비인지
  - 앱: Java 버전, JVM 옵션, 커넥션 풀 최대 크기(지금 기본값 10), Tomcat 최대 스레드(기본값 200)
  - DB: MySQL 버전, 주요 설정(`innodb_lock_wait_timeout` 기본 50초, 버퍼 풀 크기)
  - 측정 시각과 커밋 해시

노트북 측정은 같은 장비 안에서 전략끼리 상대 비교하려는 것이다. k6와 서버가 CPU를 나눠 쓰므로 절대값으로 읽지 않는다. 배포 환경에서 같은 시나리오로 다시 잰다.

## 5. 지표와 판정

### 5.1 지표

| 지표 | 정의 |
|---|---|
| 응답 시간 | 요청 종류(입장 조회, 새로고침, 선점, 확정, 취소)마다 p50, p95, p99. 측정 끝 전에 보낸 요청만 세고, 측정 끝 뒤에 받은 응답도 넣는다 |
| 5xx 비율 | 전체와 요청 종류마다 |
| 응답 없음 비율 | 제한 시간(10초) 안에 응답을 받지 못한 요청의 비율. 전체와 요청 종류마다 |
| 실패 비율 | 5xx 비율과 응답 없음 비율의 합. 판정에 쓴다 |
| 예상한 응답 | 조회·확정·취소의 `2xx`, 선점의 `201`, `409` 가운데 `SEAT_NOT_AVAILABLE`, `SEAT_LIMIT_EXCEEDED`, `ORDER_EXPIRED`. `ORDER_EXPIRED`는 부하로 서버가 늦어 확정·취소가 선점 기한을 넘긴 경우라 정상 동작이다. 5xx와 응답 없음은 실패 비율로 따로 센다 |
| 예상 밖 응답 건수 | 예상한 응답, 5xx, 응답 없음이 아닌 응답(`400`, `401`, `403`, `404`, `422`, 다른 코드의 `409` 등)의 수. 세션 흐름에서는 `ORDER_CANCELLED`, `ORDER_CONFIRMED`, `BUYER_CHANGED`, `IDEMPOTENCY_KEY_REUSED`, `SALES_NOT_OPEN`이 나올 수 없으므로 여기에 든다. 한 건이라도 있으면 무효다(4절) |
| 선점 결과 분포 | `201`과 실패 코드(`SEAT_NOT_AVAILABLE`, `SEAT_LIMIT_EXCEEDED` 등)별 건수 |
| 실제 부하 | 실제로 나온 조회 RPS와 선점 요청/초. 1절의 상한과 비교한다 |
| 매진 시간 | 판매 시작부터, 아래 보유 구간으로 셌을 때 잡혀 있는 좌석이 처음 S석이 된 시각까지. 집계 시각까지 그런 시각이 없으면 "매진 안 됨"으로 적는다 |
| 확정 중복 건수 | 한 좌석이 확정된 주문 두 개 이상에 들어 있는 수. 진짜 초과 판매다 |
| 선점 중첩 건수 | 한 좌석을 두 주문이 같은 시간에 잡고 있던 경우의 수. 아래 보유 구간이 겹치는지로 센다 |
| 1인 한도 초과 건수 | 한 구매자가 회차에서 같은 시각에 가진 좌석(보유 구간이 겹치는 주문의 좌석 합)이 4를 넘은 경우의 수 |
| 최대 처리량 | 경계 탐색에서 3번 판정(5.2절)을 지킨 가장 높은 단계(4절)를 3번 잰 선점 요청/초의 중앙값. r=32까지 지키면 하한("r=32 이상"), r=1부터 어기면 "측정 범위 아래"로 적는다(4절) |

**처리량을 고정 부하에서 비교하지 않는 이유:** 개방형 모델은 정한 속도로 요청을 넣으므로, 서버가 버티는 동안은 처리량이 넣은 속도와 같아 전략끼리 차이가 나지 않는다. 고정 부하(기준, 스트레스, 민감도)에서는 응답 시간, 오류, 불변식으로 비교하고, 처리량은 경계 탐색에서 "판정을 지킨 최대 부하"로 비교한다.

세 건수와 매진 시간은 집계 시각(2.3절)에 DB로 센다. 측정이 끝난 시점의 상태만 보면, 두 주문이 같은 좌석을 잠깐 함께 잡았다가 한쪽이 취소되거나 기한이 지난 경우를 놓친다. 그래서 확정 중복은 종료 상태로 세고, 선점 중첩과 1인 한도 초과는 주문마다 **보유 구간**을 다시 만들어 센다. 주문과 `order_seat` 행은 지우지 않으므로 다시 만들 수 있다.

| 주문 상태 | 보유 구간 |
|---|---|
| 확정 | 주문 생성 시각(`created_at`, 선점한 시각)부터 집계 시각(2.3절)까지 |
| 취소 | `created_at`부터 `updated_at`까지. 취소한 뒤에는 주문을 고치지 않으므로 `updated_at`이 취소 시각이다 |
| 만료, 기한이 지난 선점 | `created_at`부터 `held_until`까지. 만료 표시는 다른 선점이 그 좌석을 가져갈 때 늦게 붙으므로 `updated_at`을 쓰지 않는다 |
| 기한 안 선점 | `created_at`부터 집계 시각(2.3절)까지. 측정 끝 전에 확정·취소를 보내지 못한 주문도 여기에 든다 |

같은 좌석의 보유 구간 두 개가 겹치면 선점 중첩 한 건이다. 한계는 취소 시각을 `updated_at`으로 대신한다는 점이다. 취소·만료 시각을 따로 기록하는 열은 불변식 점검기(다음 이슈)에서 검토하고, 점검기가 생기면 그것으로 센다.

### 5.2 판정

| 지표 | 기준 부하 | 스트레스 부하 | 근거 |
|---|---|---|---|
| 선점 응답 시간 | p95 500ms, p99 1초 이하 | 기록만 한다 | 판단. 사용자가 흐름이 끊기지 않았다고 느끼는 1초 한계 |
| 조회 응답 시간 | p95 200ms, p99 1초 이하 | 기록만 한다 | 판단. 화면 반응 기준(INP 200ms)에서 서버 몫을 잡았다 |
| 실패 비율(5xx + 응답 없음) | 0.1% 미만 | 1% 미만 | 판단. 월간 가용성 대신 판매 오픈 구간에서 본다. 오류 대신 응답하지 않는 요청도 실패로 센다 |
| 확정 중복 | 0건 | 0건 | 불변식 |
| 선점 중첩 | 0건 | 0건 | 불변식 |
| 1인 한도 초과 | 0건 | 0건 | 불변식 |

**3번 판정:** 한 시나리오나 경계 탐색의 한 단계를 3번 잰 결과는 다음 순서로 판정한다. 앞에서 어기면 뒤는 보지 않는다. 3번은 무효(4절)가 아닌 측정 3번이고, 무효인 측정은 넣지 않고 다시 잰다.
1. 서버 실패(4절): 3번 가운데 한 번이라도 있으면 판정을 어긴 것이다. 나머지 두 번이 통과해도 같다
2. 불변식(확정 중복, 선점 중첩, 1인 한도 초과): 3번 가운데 한 번이라도 한 건이 있으면 판정을 어긴 것이다
3. 응답 시간과 실패 비율: 3번의 중앙값이 위 표의 기준 안이면 지킨 것이다

방어 없음 전략은 판정하지 않고 반복마다 확정 중복과 선점 중첩 건수를 기록한다. 그 외 전략이 어느 한 반복에서라도 확정 중복, 선점 중첩, 1인 한도 초과를 한 건이라도 내면 그 전략은 측정 결과와 상관없이 비교에서 뺀다.
