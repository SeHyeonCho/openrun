# 0003. 잠금 순서와 판단 시각

- 상태: 채택
- 날짜: 2026-11-24
- 관련: #21, #26, #28, #46, #49, #51, #52, [기능 명세](../spec/booking-flow.md) 5절, [API 명세](../spec/booking-api.md) 8절, [ADR 0002](0002-자유석-재고와-입장번호-배정.md)

## 맥락

- 좌석과 주문을 바꾸는 요청은 선점, 확정, 취소다. 여러 구매자가 같은 좌석을 동시에 노리고, 한 구매자가 여러 요청을 동시에 보내기도 한다
- 지켜야 하는 것은 초과 판매가 없을 것, 1인 최대 좌석 수를 넘지 않을 것, 같은 선점 요청 식별자는 한 번만 처리할 것, 그리고 교착 상태가 없을 것이다
- 한 요청이 선점 요청 기록, 구매자, 좌석 여러 개, 주문, 회차 순번까지 여러 행을 잠근다. 요청마다 잠그는 순서가 다르면 서로를 기다리다 교착 상태가 된다
- 선점 만료는 정리 배치 없이 선점 기한으로 판단한다(#26). 잠금을 기다리는 동안에도 시간이 흐르므로, 어느 시각을 기준으로 판단하는지에 따라 결과가 바뀐다

## 결정

### 잠금 순서

쓰기 요청은 아래 순서로만 잠근다. 필요 없는 단계는 건너뛰지만 순서를 바꾸지 않는다.

1. 선점 요청 기록: `hold_request`의 (구매자, 식별자) 유일 키. 선점에서만 넣는다. 선점 일보다 먼저 넣어서 같은 식별자의 두 번째 요청이 이 키에서 첫 요청을 기다린다(#46)
2. 구매자 잠금: `showtime_buyer`의 (회차, 구매자) 행을 `INSERT ... ON DUPLICATE KEY UPDATE` 한 문장으로 잡는다. 같은 구매자의 선점, 확정, 취소가 여기서 차례를 기다리고, 1인 최대 좌석 수는 이 잠금 아래에서 센다(#21)
3. 좌석: 좌석 ID 오름차순으로 `FOR UPDATE`. 자유석 선점은 남은 행 가운데 요청한 수만큼 `FOR UPDATE SKIP LOCKED`로 잡는다(ADR 0002)
4. 주문: `FOR UPDATE`
5. 회차 순번: `showtime_entry_sequence`. 자유석 확정에서만 잠근다(ADR 0002)

확정과 취소는 같은 메서드(`lockOwnOrder`)로 2~4단계를 잠가서, 두 경로가 순서를 따로 바꾸지 못한다(#49).

### 판단 시각

| 동작 | 기준 시각 | 이유 |
|---|---|---|
| 선점 | 요청을 받은 시각. 판매 마감만은 구매자 잠금 직후와 좌석 잠금 직후에 다시 읽은 시각으로도 확인한다 | 판매 시작과 좌석 기한은 이른 시각으로 볼수록 엄격해지지만, 판매 마감은 이른 시각으로 보면 오히려 받아 주게 된다. 경계에서 애매하면 거부하려고 마감만 다시 본다(#51) |
| 확정, 취소 | 잠금을 모두 잡은 뒤 읽은 시각 | 잠금을 기다리는 사이 기한이 지날 수 있다. 같은 구매자의 기한 직전 확정과 기한 정각의 다른 좌석 선점이 겹칠 때 1인 최대 좌석 수가 깨지는 경우도 이 순서로 막는다(#28) |
| 조회 | 첫 조회를 하기 전에 읽은 시각 | 첫 조회로 읽기 시점이 정해진 뒤 시계를 읽으면, 그사이 확정된 좌석이 "기한 지난 선점"으로 남은 수에 들어갈 수 있다(#52) |

- 시각 경계는 "그 시각부터"로 본다. 판매 시작 시각 정각에는 판매가 열려 있고, 선점 기한 정각에는 선점이 끝나 있다
- 서버 시계는 마이크로초 아래를 버려 DB에 저장한 시각과 같은 정밀도로 비교한다(#28)

### 격리 수준

- 선점, 확정, 취소는 `READ_COMMITTED`로 실행한다. 잠금을 기다린 뒤에는 다른 트랜잭션이 커밋한 값을 읽어야 하는데, MySQL 기본값(`REPEATABLE_READ`)에서는 잠금을 잡아도 1인 수량을 이전 스냅샷으로 센다(#21)
- 조회와 선점 요청 기록의 재생은 `REPEATABLE_READ` 읽기 트랜잭션으로 실행해 여러 번 읽어도 한 시점으로 보이게 한다(#46, #52)

## 버린 대안

- 구매자 잠금 행을 별도 트랜잭션으로 먼저 만들기: 요청이 몰리면 요청 하나가 커넥션을 두 개씩 써서 커넥션 풀이 바닥날 수 있다(#21)
- 잠금 없이 조건부 `UPDATE`만 쓰기: 좌석 하나는 지킬 수 있지만, 여러 좌석과 1인 최대 좌석 수를 한 번에 지키려면 결국 구매자 단위의 차례가 필요하다. 전략 비교(P1)에서 비교군으로 다시 잰다
- Redis 분산 락: 서버가 한 대인 동안은 DB 잠금과 결과가 같고 장애 지점만 늘어난다. 서버를 여러 대로 늘리는 단계(P6)에서 비교한다
- 만료 정리 배치: 만료 순간에 해야 할 일(가상계좌 닫기, 늦은 입금 환불)은 결제(P2)에서 생겨서 그때까지 미룬다(#26)
- 모든 판단을 요청을 받은 시각으로 하기: 잠금을 기다리는 사이 판매 마감이 지나도 주문이 생긴다(#51)

## 결과

- 동작마다 동시성 테스트로 확인했다. 같은 좌석을 여러 구매자가 선점, 같은 구매자의 동시 선점, 같은 식별자의 동시 요청, 취소와 확정의 경합, 판매 마감 경계의 자유석 선점에서 초과 판매와 1인 최대 좌석 수 초과가 없었다
- 새 쓰기 경로도 이 순서를 따라야 한다. CodeRabbit 서버 코드 지침(`.coderabbit.yaml`)이 같은 순서로 리뷰한다
- 같은 구매자의 요청과 같은 회차의 자유석 확정은 차례를 기다린다. 얼마나 기다리는지는 아직 재지 않았고 전략 비교(P1)에서 잰다
